# ATLAS #520: exact signed action retry

Based on npm's @bsv/wallet-toolbox 2.10.2 SLSA-attested source e0838bc37ccaa2f13b8977bc409f437f611b0987. Maintained source branch: Quaakee/ts-stack atlas/589-exact-resume-520.2 (codex/520-exact-signed-resume plus the ATLAS #589 repair). Artifact identity is @bsv/wallet-toolbox@2.10.2-atlas.520.2, distributed as an immutable tarball, not published to the upstream npm namespace. It supersedes 2.10.2-atlas.520.1, whose retries could be committed outside their sendWith set.

Public API remains createAction({description, options:{sendWith:[originalTxid]}}). A failed/invalid signed action can requeue only the original rawTx/inputBEEF after transaction verification using the existing storage ancestry expansion, one owned outgoing transaction/notification correlation, complete one-to-one signed-vout and caller-owned output checks and input reservation conflict checks. Request, action, and input/output bookkeeping of every retry in a sendWith set change in one storage transaction, all or nothing: every retry is first planned read-only, every row lock of every retry (requests, then actions, then outputs, each in ascending order) is acquired before the first snapshot read, and each retry then runs every check above, so a refusal of any retry rolls back all of them. Ambiguous or conflicting lineage throws; callers retain the original action and must not construct a replacement.

The share's one lookup is the only decision for the set (#589). A retry is admitted only while that lookup still shows its planned failed request and every other member of the same sendWith set is already sendable or already sent. Otherwise no retry state is committed, and the caller's results report the retry as failed or the call throws. Ordinary sendWith sharing is unchanged from 2.10.2: the ready members of an incomplete set are still shared (an immediate share then throws after posting them), but a retry never joins such a set. With acceptDelayedBroadcast the retries commit inside the transaction that schedules the set, under one batch when the set has several members. In immediate mode they commit after the exact-binding checks and merged-BEEF verification, in one transaction that also revalidates every exact binding in the set and records the set's batch; only the post follows it. A retry that another caller requeued or sent meanwhile is kept as found only while it stays sendable or already sent; anything else aborts that transaction.

The durable request history marks this exact retry with the authorized user and action IDs. Sharing, delayed scheduling, and post-result reconciliation revalidate that binding; newly shared or foreign notifications are refused. Subsequent broadcast failures are indeterminate (existing serviceError/sending review results) unless the exact txid is positively accepted or reported known/mined. Known/mined only returns unproven; the existing validated proof path owns completed status. A failed service response, unknown status, timeout, abort success or local failure label is never proof of retirement. No new terminal witness API is provided. listFailedActions(true) is not used and its legacy convenience behavior is not repaired here.

Limits of the set guarantee: once an immediate set's retries commit, an exception from the post step, or a crash before it, leaves the set queued (the existing durable queue), and the caller receives that exception rather than failed results. A new transaction created by the same createAction is committed before the set's retries are decided; with acceptDelayedBroadcast it is already queued for the monitor, so a retry refusal thrown afterwards does not withdraw it.

The generic failed request path reconstructs input reservations only when no later action owns them. It refuses ambiguous multi-user/shared request notification lineage. Existing WalletInterface and request wire formats remain unchanged; retry history is internal. No wallet identity, grant set, envelope semantics or application mint flag changes.

Regression runner: test/atlas/run-exact-resume.cjs over test/atlas/exact-resume.cjs, executed using tsx against source, and with imports rewritten to the exact packed package for clean-consumer qualification. The #589 scenarios (incomplete-set, poc2-multi, poc2-transient, poc2-transient-delayed, poc2-ordering, poc2-ordering-delayed) assert that a refused or unadmitted set leaves the request invalid, the action failed and its input unreserved, and that the monitor then broadcasts nothing; duplicate-member and duplicate-member-delayed assert that a retry listed twice is reported consistently at both positions. Tests own SQLite databases and MockServices chains; no external network, wallet, provider, funds or credential store is accessed. The qualification harness exercises SQLite and task-owned MySQL/InnoDB REPEATABLE-READ concurrency/restart, including independent wallet connection pools. IndexedDB and live remote deployment remain unqualified. The source build is additionally checked independently against the package's original SDK dependency and adoption SDK artifact.
